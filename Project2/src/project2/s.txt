For my second project, I took my virtual calendar pet from the console and rebuilt it as a proper window app. Just like before, you name your pet when it starts, and it shows your events for the day. But now the events are saved in a database instead of a text file, and you can add new ones with a form.

_Show the package list in your IDE._

The code is split into five packages: model, view, controller, service and data. It follows the Model View Controller pattern, with a service layer and a data layer added on.

Let’s start with the model. The Pet class looks after the pet’s state, using an enum with three states: sleeping, awake and active. If the pet is asleep, the calendar buttons don’t work, and that rule lives inside the Pet class so it can’t be skipped. The Event class is immutable. Its fields are private and final, with no setters, so that’s my example of encapsulation.

The view is everything you see on screen. Pet View is the main window. Pet Picture Panel loads one picture for each state, shows the right one, and writes the pet’s name underneath. Add Event Dialog is the form for new events. None of these classes know anything about the database or the pet’s rules.

The controller connects it all together. It’s the only class that knows about the model, the view and the service. When you click a button, it tells the pet or the service what to do, then updates the window. It also runs a timer that checks every second whether the pet should fall asleep.

The pet and the service use the Observer pattern. They just announce when something changes, and the controller listens, so they never need to know about the window.

Next is the service layer, Calendar Service. It checks that an event is valid before saving it. If there are several mistakes, it shows them all at once.

Last is the data layer. Event Dao is an interface, and Jdbc Event Dao uses it to talk to the Derby database. It uses prepared statements, so what the user types can’t change the SQL. A factory creates it, so I could swap in a different kind of storage later. The Database class is a singleton, because Derby only allows one connection at a time. And if anything goes wrong with SQL, it’s turned into my own Data Access Exception, so the rest of the program doesn’t need to know SQL is underneath.

_Run the program._
First, a pop-up asks me to name my pet. I’ll type a name and press Enter. If I leave it empty, it just asks again.
The pet starts off asleep, with its eyes closed. The window shows today’s events from the database, and the bottom line shows how many events are stored.
_Click Next._  
If I press Next, nothing happens, because the pet is asleep. It tells me to wake the pet up first.
_Click the pet picture._  
Clicking the pet wakes it up, and the picture and the speech both change.
_Click Next, Back, then Today._  
Now the buttons work. The pet goes active for a moment, and the date and events update.
_Click Rename pet._  
I can change the name any time with this button. The window title, the speech and the name under the picture all update straight away.
_Click Add event, then press Add with the title empty._  
This opens the form. If I leave the title empty and press Add, the form stays open and tells me what’s wrong, so I don’t lose what I typed.
_Fill in a title and a time, then press Add._  
Now the form closes, and the new event appears in the list. The stored count goes up by one.
_Wait for the pet to fall asleep._  
If I leave the pet alone, it falls asleep by itself and the calendar jumps back to today.

So this version has a full window, validation, and a database that keeps my events. Thanks for watching!
